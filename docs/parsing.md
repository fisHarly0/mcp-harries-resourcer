# 搜索与正文解析隔离

下载完成后，服务将 HTML 交给独立 Python 进程：正文生成纯文本、Markdown 和引用元数据，Bing／DuckDuckGo 搜索页生成标题、链接和摘要。每个进程只处理一页，完成即退出；缓存命中不再启动解析进程。同 URL 的并发调用仍共享一次下载和解析。

这样复杂 HTML 的正文提取不会持续阻塞 MCP 主事件循环。取消正在执行的任务时，可以终止对应解析进程并等待回收；仅取消线程或执行器里的 Future 无法停止已开始的计算。进程管理依据 [Python asyncio 子进程接口](https://docs.python.org/3.10/library/asyncio-subprocess.html)和[执行器的取消语义](https://docs.python.org/3.10/library/concurrent.futures.html)，实现独立编写。

## 默认边界

| 项目 | 默认值 | 调整方式 |
|---|---|---|
| 全局并行 HTML 解析 | 2 个进程 | `RESOURCER_PARSE_CONCURRENCY`，1–5 |
| 单次 HTML 解析预算 | 20 秒 | `RESOURCER_PARSE_TIMEOUT_SECONDS`，1–120 |
| 解析结果传输上限 | 32 MiB | 固定上限，包含正文或搜索结果及 JSON 元数据 |

解析预算包含等待解析名额、启动进程、提取、传输结果和正常回收。单页 60 秒默认预算与整批截止时间继续生效，哪个先到就先中止。正文工作仍占用已有的全局抓取名额，避免下载无限堆积后等待解析。搜索与正文共享解析名额；正文繁忙时搜索也会排队，反之亦然。搜索的单引擎总预算和批量截止时间包含解析阶段。

超时和主动取消会先终止解析进程，再排空管道并等待退出，之后释放名额。取消发生在进程启动期间、或清理期间再次收到取消，也会等到已启动进程被回收。一个页面取消不会终止其他页面；共享下载的跟随者取消也不会影响拥有者。

## 结果与失败

成功页面包含 `parse_info.mode="subprocess"` 和 `elapsed_seconds`，记录这次解析阶段的耗时。命中缓存时保留原始记录，结合 `cached` 判断本次是否执行。

| 错误码 | 含义 |
|---|---|
| `parse_deadline` | 解析排队或运行超过解析预算 |
| `parse_worker_failed` | 进程无法启动、异常退出或输出格式无效 |
| `parse_output_too_large` | 解析结果超过 32 MiB |
| `deadline` | 单页总预算先到期 |
| `batch_deadline` | 整批预算先到期 |

搜索解析的进程级失败在对应 `attempts` 中附 `error_code`；原有 fallback 会尝试下一个引擎，merge 会保留其他引擎结果。明确的无结果页仍是成功空结果，验证码或未知布局仍是搜索失败。主动取消直接退出并回收进程，不继续尝试下一个引擎。

失败不会缓存半份正文。正常解析中只有一种格式失败时，另一种格式仍可使用；进程级失败则整页失败。不会自动回到主线程解析。

## 开销和限制

- 每个新页面都有解释器和依赖启动开销。短页面可能比以前慢；缓存仍能避免重复解析。
- 进程数量和传输大小有上限，但没有操作系统级内存额度，也没有 CPU 时间配额。复杂页面可占用显著内存，低内存环境可将并发设为 1。
- 正文选择、Markdown 渲染和 Bing／DuckDuckGo 搜索 HTML 解析在子进程中；SearXNG JSON 解析、请求准备、HTML 字符解码和父子进程传输的 JSON 序列化仍在主进程。已提供 [工具级 MCP 进度](progress.md)，没有单页解析内部的完成百分比。
- 进程创建和回收依赖操作系统，不能保证精确在截止时刻返回。这里覆盖正常超时、取消与服务清理，不承诺宿主被强杀或机器断电时的回收行为。
- 使用同一 Python 环境和绝对脚本路径，子进程不打开窗口，不向 MCP stdout 写日志。Windows 虚拟环境采用 [CPython multiprocessing 的启动方式](https://github.com/python/cpython/blob/3.12/Lib/multiprocessing/popen_spawn_win32.py)，直接持有实际解释器的进程句柄。

## 验证

测试使用真实解析进程，检查持续 CPU 计算期间主循环仍可执行、取消/超时后进程已退出、排队取消不启动新进程、重复取消、启动期间取消、独立调用互不影响、输出超限和崩溃恢复。整批测试检查已完成正文保留、解析失败不进缓存、下一次调用能恢复。

真实 MCP stdio 测试发送取消通知，并在整批到期后检查活动解析进程、共享下载记录和缓存状态，再验证同 URL 重试恢复。真实联网读取 Python asyncio 任务文档的结果仍为 61,680 字符 Markdown、34 个代码块；该次解析阶段约 1.1 秒，格式切换和续读命中缓存。

Python 3.10 的 CI 暴露了重复取消可能提前打断外层 `wait_for` 清理等待的问题。现在解析、单页、搜索和网络的超时边界都继续持有子任务直到清理完成；整批任务回收也防止再次取消中断等待。回归测试模拟外层提前返回取消，分别验证直接解析与完整单页调用都等待实际子进程退出。

2026-10-04，Windows + Python 3.12 对 1,047,741 字节的合成 HTML（1,000 个代码块、1,000 张表格）测量：解析阶段约 5.9 秒，子进程采样 CPU 时间约 5.3 秒、峰值工作集约 77 MiB；20 毫秒间隔的主循环探测最大观测间隔约 34 毫秒，结束后活动解析进程为 0。这是本机单次样本，不代表所有网页或机器的性能。


## 搜索解析响应性测量

Python 的[异步开发说明](https://docs.python.org/3/library/asyncio-dev.html#running-blocking-code)指出，直接执行 CPU 密集任务会推迟同一事件循环中的其他任务。0.2.2 的搜索路径不仅在主循环中解析，还重复构建 HTML 树；0.2.3 将识别验证码、提取结果和判断空页合并到同一棵树，并在子进程执行。

2026-10-04，Windows + Python 3.12.12，固定合成 Bing HTML：10 条候选为 1,214 字节，5,000 条为 622,804 字节，均只返回前 10 条。20 毫秒间隔观察主循环，不包含网络等待。修改前 5,000 条样本单次解析约 1.235 秒，主循环最长观测间隔也是 1.235 秒。

修改后用同一份单次建树解析器分别在主循环和子进程运行，各测三次：

| 样本 | 执行位置 | 解析耗时范围 | 主循环最大观测间隔 |
|---|---|---|---|
| 10 条 | 主循环（仅对照） | 0.002–0.007 秒 | 34 毫秒 |
| 10 条 | 子进程 | 0.159–0.177 秒 | 36 毫秒 |
| 5,000 条 | 主循环（仅对照） | 0.671–0.837 秒 | 837 毫秒 |
| 5,000 条 | 子进程 | 0.839–0.878 秒 | 36 毫秒 |

全部返回预期的 10 条结果，结束后活动子进程为 0。结果说明该样本中的主循环阻塞得到缓解，也显示短页启动成本；并非真实搜索质量、吞吐量或其他机器的性能保证。历史改前单次测量和本次三次测量不作为严格的总耗时加速比。

安装运行依赖后，可在源码目录复现当前两种执行位置的比较：

```powershell
python scripts/benchmark_search_parsing.py --repeats 3 --output search-parsing.json
```

测试另覆盖搜索和正文共用名额、搜索排队超时、CPU 忙碌时重复取消、启动途中取消、无效结果结构、崩溃及输出超限后的恢复。真实 MCP 取消通知验证子进程清理，merge 截止验证保留另一个引擎已完成的来源；安装包从无关工作目录执行真实搜索解析进程。
