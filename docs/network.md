# 网络恢复与资源限制

搜索和网页抓取共用 HTTP 请求策略。目的在于恢复短暂故障，同时为等待、跳转和响应体设置边界。默认值不需要额外依赖；环境变量修改后重新连接 MCP 服务。

## 默认行为

- 最多追加 **1 次重试**，即初次请求加一次恢复尝试。
- `429`、`502`、`503`、`504` 可以重试；连接失败、HTTPX 超时、读取失败和远端协议中断也可以重试。
- `202`、验证码、`401/403/404`、解析失败、内容过大和压缩数据无效不重试。普通 `500` 当前也不重试。
- 有有效 `Retry-After` 时按秒数或 HTTP 日期等待；没有有效值时，重试前依次等待 1、2、4 秒（取决于配置次数）。
- 等待超过剩余时间预算时，保留本次失败，不缩短网站要求的等待时间。已知的等待期按协议、主机和端口保存在进程内，同一来源的后续请求也需要等待；其他来源可继续。
- 初次请求、重试、HTTP 跳转均经过原有搜索／正文限速。每次尝试最多跟随 **5 次跳转**；跳转响应体和错误响应体不下载。
- 正文抓取的全局最多 5 路并发仍然有效，重试期间也占用该抓取名额。同 URL 的进行中请求继续共享下载。

等待期最多分别记录 256 个来源。如果同时活跃的来源更多，额外等待合并为进程级等待期，避免无限积累状态，也避免直接遗忘网站要求的等待。这种极端情况下其他来源也可能暂时等待。状态随服务重启清空。

## 时间预算的范围

`RESOURCER_REQUEST_TIMEOUT_SECONDS` 默认 **60 秒**，允许 1–300 秒。

单个 HTTP 请求流程包含限速、站点等待期、连接、所有跳转、读取、重试和退避。一个搜索引擎尝试还将 Bing 首页恢复请求包含在同一个预算中；依次切换多个引擎时，每个引擎尝试有独立预算。

单页抓取还把共享并发池排队、同 URL 下载等待计入预算。批量工具自身的分批等待不计入每页预算，**目前没有整批调用总时限**。因此一批很多页面可能明显超过 60 秒，后续将继续增加整批预算与部分结果返回。

这是异步 I/O 的协作式时间限制，不是独立进程的 CPU 硬限制。HTML 提取目前仍是同步操作，不能在解析函数内部强制中断。默认 HTTPX 分阶段超时仍为 25 秒，与总预算同时生效。

取消调用会中断等待和当前下载，并关闭响应。取消共享下载的跟随者不会取消拥有者；拥有者取消后，仍在等待的调用可使用自己的客户端重新尝试。失败与超时不会留下永久占用的下载记录。

## 响应体预算

`RESOURCER_RESPONSE_MAX_BYTES` 默认 **8 MiB（8388608 字节）**，允许 1024–67108864。传输数据与解压后数据分别受这个上限约束：

1. `Content-Length` 已超限时，在读取正文前终止。
2. 长度未知时，以最多 64 KiB 的块读取并检查累计大小。
3. 请求声明支持 gzip、deflate；使用带输出上限的增量解压，同时检查解压后大小。gzip 多成员、标准及原始 deflate 均有测试。
4. 超限、压缩数据无效或不完整时，关闭响应并报错，不把部分内容交给正文提取，也不缓存部分内容。

未压缩响应同样受限。其他压缩方式（例如服务端忽略请求声明而返回 Brotli）以及叠加多层编码目前会明确报告不支持。

字节预算不同于 `max_chars`：前者限制下载输入，后者限制提取后返回给模型的字符数。`max_chars=0` 不会关闭下载上限。这也不是“整个进程最多占 8 MiB 内存”的保证，响应块、正文副本和 HTML 解析器仍有额外开销。

## 配置与结果

| 环境变量 | 默认值 | 允许范围 |
|---|---|---|
| `RESOURCER_HTTP_RETRIES` | 1 | 0–3；0 关闭追加重试，仍遵守已记录的等待期 |
| `RESOURCER_REQUEST_TIMEOUT_SECONDS` | 60 | 1–300 秒 |
| `RESOURCER_RESPONSE_MAX_BYTES` | 8388608 | 1024–67108864 字节 |

无效设置在 stderr 警告并回退默认值，不会悄悄关闭限制。无需修改现有工具调用参数。

正文 JSON 的 `request_info` 包含成功完成网络流程的请求次数、重试次数、解压后响应字节数和网络流程耗时。命中缓存时保留的是原始抓取记录，应结合 `cached` 判断本次是否发起网络请求。

策略失败时正文 JSON 使用 `ok=false`、空 `text`，并提供 `error_code`：

| 错误码 | 含义 |
|---|---|
| `deadline` | 时间预算用尽，或剩余预算不足以恢复连接故障 |
| `cooldown` | 已记录的站点等待期超过本次预算；可表示时附剩余秒数 |
| `response_too_large` | 传输数据或解压后数据超限 |
| `redirect_limit` | 跳转次数超限 |
| `content_encoding` | 压缩方式不支持、压缩数据损坏或不完整 |
| `http_status` | 最终 HTTP 状态失败；`request_info` 中可附网站要求的等待秒数 |

搜索仍通过 `diagnostics` 和 `attempts` 保留失败原因，再按所选搜索策略继续处理其他引擎。网络故障不会变成“未找到资料”。

## 验证与参考

离线测试覆盖秒数／日期等待、跨调用等待期、恢复次数、所有跳转限速、跳转上限、未知长度流、压缩膨胀、截断压缩流、取消、排队超时和缓存一致性。另用真实 MCP 子进程访问本地 HTTP 服务，验证 503 后恢复、超大响应、gzip 膨胀、持续缓慢发送及 429 后禁止提前访问同一来源。

2026-10-04 真实联网验证：MCP 成功提取 [Python asyncio 官方文档](https://docs.python.org/3/library/asyncio.html)，响应正文 25411 字节，1 次请求、0 次重试；第二次读取命中缓存。官方文档搜索返回 3 条来源。它证明当前网络流程可用，不代表所有网站均能抓取。

设计参考：[DuckDuckGo MCP Server](https://github.com/nickclyde/duckduckgo-mcp-server) 的有限恢复思路；具体等待语义依据 [HTTP Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)，下载与关闭流程依据 [HTTPX 异步流接口](https://www.python-httpx.org/async/)。实现独立编写，总预算额外覆盖了 HTTPX [分阶段超时](https://www.python-httpx.org/advanced/timeouts/)无法单独约束的连续慢速下载。
